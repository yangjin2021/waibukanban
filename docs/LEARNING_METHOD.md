# 项目式学习方法

更新时间：2026-08-09

## 0. 永远不要忘记最终目标

本项目学习 Python 不是为了“学完一门语言”，最终目标始终是：

> **用 Python 做出一个类似 Solver 的 Poker GTO 智能系统。**

以后所有学习内容都要回答：

> **这个知识怎样通过 Python 帮助最终 Poker Solver-like AI？**

路线：

```text
Python 基础
→ Poker 数据结构
→ Card / Range / Action / State
→ Solver 数据读取与自动化
→ Dataset
→ NumPy / PyTorch
→ 模型训练与评估
→ Game Tree / CFR
→ 推理与决策
→ 类 Solver 的 Poker GTO 智能系统
```

## 1. 只用 Python 教学

正式编程教学只使用 Python。

- 不使用 Lisp / S-expression 或第二门编程语言做类比。
- 卡住时改用更小 Python、人话、真实数据、箭头、树、盒子、表格、比喻、展开 / 压缩、正向 / 逆向追踪。
- 所有正式 AI / 工程实现最终回到 Python。

## 2. 核心哲学：Code drives learning

> **代码是推动课程与项目的第一动力。**

人工智能最终要通过代码实现，所以不把代码当理论课最后的“例子”，而是让代码成为知识出现的入口。

```text
SHOW CODE
→ 读代码
→ 遇到问题
→ 补当前需要的知识
→ 回到代码验证
→ 接入 Poker AI
→ 下一段代码继续推进
```

项目进度优先问：

> **今天又读懂、写出、运行或验证了哪段 Python？**

## 3. 每课固定三类辅助

以后每一课除了主代码外，都固定保留三类辅助：

```text
① 代码识字
→ PyCharm 颜色 + token 属性 + 符号 + 名字来源

② 理解镜头
→ 真实数据 + 数据流 + 比喻 / 解释

③ 代码哲学
→ 当前代码背后的编程思想 / 工程直觉
```

这些内容可以紧凑，但不完全省略。目标是让用户不仅知道“代码运行了什么”，还逐渐知道“代码怎么看、为什么这么组织、这种结构以后还会在哪里出现”。

## 4. 代码识字能力是基础能力

目标不仅是懂程序逻辑，还要逐渐做到：

> **看到 Python 代码表面，就能读出大部分元素是什么。**

因此每课辅助识别：

```text
PyCharm 颜色
代码单词 / token 属性
Python 符号 / 标点
名字是谁规定的、能不能改
```

例如：

```text
def      → Python 关键字
rank     → 参数 / 变量名
append   → list 方法
"As"     → 字符串字面量
[]       → 当前上下文中的 list / 下标 / 切片
()       → 当前上下文中的调用 / 参数 / 分组等
{}       → 当前上下文中的 dict / set
=        → 赋值
==       → 比较是否相等
.        → 访问对象属性 / 方法
```

尤其注意：**符号必须结合上下文解释。** `[]` 不能永远死背成“列表”。

如果用户当前 PyCharm 配色已知，直接说明实际颜色；未知时不猜颜色名称，但仍解释 token 属性。

## 4.1 代码颜色必须尽量真实渲染

用户正在建立“看颜色识别代码属性”的能力，因此以后不仅要在文字里解释颜色，还要在界面允许时 **把代码本身按语法类别真正渲染出颜色**。

默认规则：

1. 普通 Python 代码块必须使用 Python 语法代码块，让界面自动进行语法高亮；不要为了省事把 Python 放进纯文本代码块。
2. 交互式课件 / 答题器 / 可视化中出现 Python 时，不能长期使用整块单色 `<pre><code>`。如果界面允许，应给关键 token 做语法着色，让字符串、数字、关键字、函数 / 方法、变量名、符号在视觉上可区分。
3. **尽量贴近用户实际 PyCharm 的阅读体验。** 如果已经知道用户的 PyCharm Theme / Color Scheme，则优先按该配置解释和模拟；如果不知道具体方案，不编造“你那里一定是某个颜色”，只说明 token 类别，并使用清晰、稳定、可区分的教学配色。
4. 颜色不能替代概念。每次首次出现重要颜色时，同时说明它代表的代码属性，例如：

```text
"132" → 字符串字面量（str）
132   → 整数字面量（int）
if    → Python 关键字
len   → 内置函数
state → 变量名
.get  → 方法访问 / 方法名
```

5. 同一个教学界面内，**同类 token 尽量保持同一种颜色语义**，不要同一页里反复换色造成新的认知负担。
6. 颜色必须与层级教学配合。例如展示 `"132"`、`["132"]`、`[["132"]]` 时，字符串 `"132"` 保持同类颜色，而 `[]` 的嵌套通过括号、缩进、结构线或说明体现，让用户同时看到“内容类型”和“容器层级”。
7. 交互题的题干代码也遵守这一规则；不能只把讲解示例上色、正式测试题又全部变成单色。

目标是让用户逐步建立：

> **颜色是辅助线索，token 属性才是真正含义；最终即使换了主题颜色，也能认出代码。**

## 5. 比喻必须回到代码

每课至少给一个能帮助理解当前代码的比喻 / 解释镜头，例如：

```text
座位编号
抽屉 / 盒子
流水线
快递交接
菜单 / 点单
扑克桌上的实际动作
```

比喻只负责建立直觉，之后必须明确映射回真实 Python。不能为了好懂而改变真实执行顺序、数据流或语义。

## 6. 代码哲学逐课积累

每课后半段补 1～2 个直接对应当前代码的思想，例如：

```text
数据比名字更重要
结构比记忆更重要
索引是位置，不是内容
函数是在给处理建立边界
参数让函数可复用
return 是函数的对外出口
循环是在把同一个规则应用到不同数据
条件是在程序中制造分叉
抽象是为了减少重复和错误
Small → Correct → Scale
可读代码首先是给人读
AI 工程仍然是数据 → 处理 → 输出
```

不讲空泛口号，要指出它对应当前代码里的哪一行 / 哪个结构。

## 7. 疑问先诊断前置缺口

用户出现疑问时，先问：

> **这是真的新知识难，还是以前某个基础没有学稳？**

默认采用：

```text
Diagnose
↓
找到当前疑问依赖的最小前置缺口
↓
Backfill
↓
用短 Python 补上
↓
Return
↓
重新回到原来的当前代码
```

优先检查：代码识字、Python 基础、控制结构、数据流、作用域 / 对象 / 方法、Poker 项目基础、数学 / AI 前置。

原则：**讲过不等于学会。** 只补最小缺口，不整章重讲。

## 7.1 交互式分层诊断测试

当用户对某个概念反复混淆，或者连续解释后仍无法稳定判断代码结果时，不要只继续重复讲解，也不要只问“懂了吗”。应主动判断是否更适合切换成 **交互式分层测试**。

适用情况包括但不限于：

```text
int / str 混淆
list / str 混淆
一层 list / 多层 list 混淆
dict 的 key / value 混淆
[] 的“创建容器 / 按索引或 key 取值”混淆
= / == 混淆
len() 数哪一层不清楚
in 在哪一层比较不清楚
.get() 的 key / 默认值 / 返回值不清楚
if 最终为什么 True / False 不清楚
复杂 Poker Range / State 数据流无法逐步展开
```

推荐测试结构：

```text
最小概念题
↓
两个易混概念对比
↓
加入一层容器
↓
加入嵌套容器
↓
加入 dict / 索引 / .get()
↓
加入 in / == / if
↓
混合题
↓
真实 Poker Range / State Boss 题
```

测试必须遵守：

1. **一层一层变复杂。** 前一层未稳定，不直接跳到更复杂层。
2. **故意加入“长得很像但类型 / 层级不同”的代码。** 例如 `"132"`、`["132"]`、`[["132"]]`。
3. **优先让用户直接点击、选择或填写答案。** 题目较多时，如果界面能力允许，优先做成交互式答题器，而不是要求用户手工抄写十几个题号。
4. **交互题里的 Python 代码也必须尽量语法着色。** 颜色规则与正式课程一致，让测试同时训练代码识字；不能因为进入答题界面就退回单色代码。
5. **不要只给总分。** 必须按知识点统计错误，定位到具体前置缺口，例如 `int/str`、变量与数据、list 层级、dict 取值、`in` 层级、`.get()` 数据流等。
6. **根据总体答题模式诊断，而不是只看单题。** 多道同类题连续错误，说明该基础层尚未建立；只错一道则优先判断为局部失误。
7. **错题解释继续使用最小 Python。** 把复杂表达式逐步替换成真实值，最后压缩成最小判断，例如把复杂 Range 判断化成 `["132"] in [["123"], ["132"]]`。
8. **诊断后 Backfill。** 只补最低层的真实漏洞，再重新测试该层；通过后再回到原项目代码。
9. **最终必须回到真实项目。** 测试不是独立刷题，最后要让用户能读懂、修改或预测当前 Poker AI 代码。

目标不是“做题得高分”，而是建立可验证的掌握标准：

> **用户能够不运行代码，逐层说出数据是什么类型、当前容器有几层、取出了什么值、比较发生在哪一层，以及最终为什么得到这个结果。**

## 8. 最小核心递增法

看不懂时先缩代码：

```text
真实代码
→ 最小核心 Python
→ 读懂代码表面
→ 颜色 / token / 符号
→ 功能 / 输入 / 处理 / 输出
→ 真实值跑一轮
→ 比喻 / 解释
→ 代码哲学
→ 逐层还原
→ 回到项目
```

如果某行再删除就破坏核心逻辑，要明确说：

> **这一行是核心，不能再砍了。**

简化不能改变真实逻辑。

## 9. 四个骨架问题

每个函数优先识别：

```text
功能名字
输入
处理
输出
```

再看：

```text
谁调用它
数据从哪里来
结果到哪里去
它属于 Poker AI 的哪个更大功能
```

Dataset、Model、Loss、推理、CFR、Game Tree 都继续沿用这套骨架。

## 10. 真实数据与数据流

抽象代码尽量拿真实 Poker 数据跑一次。

真正连接变量的是赋值、参数传递、`return`、容器写入等数据流，不是名字一样。

以后 Dataset、Tensor、Model Input、Policy、EV 都用同样的数据流思维理解。

## 11. 数学和 AI 按代码需要出现

不为了“完整课程”提前堆理论。

```text
Python 代码出现需求
→ 补最少必要数学 / AI 概念
→ 马上用 Python 表达
→ 跑数据
→ 看输出
→ 接回 Poker AI
```

例如：

```text
百分数        → Range Frequency
概率          → Strategy
组合          → 1326 Combos
加权平均      → Range EV
向量          → Policy / Range
矩阵          → Batch / Dataset
函数          → Model(x) = y
误差          → Loss
导数          → Gradient
概率分布      → Softmax
条件概率      → Range Update
博弈树 / Regret → CFR
```

## 12. 每次学习都变成项目资产

每次课程尽量留下：Python 代码、测试、数据样本、模型、实验记录、文档或当前进度更新。

每完成一个可验证小步骤，优先更新 `CURRENT_STATE.md`。

## 13. 一句话路线

> **SHOW CODE；让 Python 代码成为课程与项目的第一动力；每课固定用 PyCharm 颜色、token 属性、符号和名字来源帮助读代码；界面允许时把代码本身真正做语法着色，交互题也保持一致；再用真实数据、比喻和解释建立直觉，并逐课补充代码哲学；用户一有疑问就 Diagnose → Backfill → Return；反复混淆时优先判断是否切换成“交互式分层测试 → 错因诊断 → 精准补课 → 回到真实项目”；每学会一点都放回 Poker AI 项目。**
