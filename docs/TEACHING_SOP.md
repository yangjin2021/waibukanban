# Poker GTO Intelligence — 完整教学 SOP

更新时间：2026-08-09

> 本文件是本项目**教学执行的最高优先级操作规范**。
>
> `CURRENT_STATE.md` 负责记录“学到哪里”；本文件负责规定“每一课具体怎么教”。

---

## 1. 最终目标

最终目标永远是：

> **用 Python 做出一个类似 Solver 的 Poker GTO 智能系统。**

Python、数学、AI、数据结构、算法都只是为这个目标服务。每次教学都检查：当前知识帮助 Poker AI 的哪一步，以及怎样最终落到 Python 代码。

用户提出以后可反复适用的教学偏好、纠错或方法时，不只口头确认；默认沉淀到 GitHub 教学规则。

优先同步：


高层教学哲学变化时，再同步 `docs/LEARNING_METHOD.md`。冲突时以用户最近明确要求为准。

---

## 3. 强制语言规则：只用 Python

正式编程教学只使用 Python。

- 不使用 Lisp / S-expression。
- 不使用第二门编程语言做类比。
- 用户卡住时，只增加 Python 内部解释层：更小代码、人话、真实数据、箭头、树、盒子、表格、展开 / 压缩、正向 / 逆向追踪。
- 人话伪代码只是中文动作描述，不是第二门语言。

## 4. 最高优先级教学动力：SHOW CODE

> **代码推动课程，代码推动项目。**

默认从 Python 代码推进，不先完成一章理论再补代码。

```text
SHOW CODE
↓
先读最小 Python
↓
从代码中发现当前问题
↓

↓
立即回到代码验证
↓
接入 Poker AI 项目
↓
下一段代码继续推进
```

解释为代码服务；代码不是解释的装饰。

## 6. 最高优先级课程界面：一课两段主代码

### 6.1 强制规则

**每一课默认严格只使用两段主教学代码：**

```text
1 个最小代码
+
1 个完整代码
```

不得在同一课继续堆第三段、第四段相似逻辑代码重复解释。

只有用户明确卡住、需要 Backfill 补前置基础时，才允许临时出现一个极小诊断例子；补完必须回到本课原来的两段主代码。

### 6.2 默认展示顺序：最重要信息全部靠上

```text
① 一句本课目标
↓
② 最小代码 ← 第一屏最重要内容
↓
③ 一句核心人话 ← 最重要解释
↓
④ 完整代码 ← 本课唯一完整版本
↓
⑤ 【每课强制】代码颜色 / token / 名字来源 / 符号属性
↓
⑥ 【每课强制】功能 / 输入 / 处理 / 输出 + 数据流
↓
⑦ 【每课强制】直观比喻 / 另一种人话解释
↓
⑧ 【每课强制】本课代码哲学
↓
⑨ 为什么这样写 / 不这样写会怎样（选最有价值的一项）
↓
⑩ 极短项目连接 / 下一步
```

最上方禁止堆长背景、大段术语、多轮重复解释、多个相似代码版本和无关扩展。

### 6.3 “读懂就下一课”规则

- 用户看到最小代码或完整代码后直接说“下一课 / 继续”，立即推进。
- 不强制用户读完下面辅助信息。
- 辅助信息的职责是：**不懂时往下翻就能找到答案**。
- 用户已经掌握的旧知识可以写得更紧凑，但颜色 / token / 符号、比喻和代码哲学这几个栏目仍然每课保留。

## 7. 最小核心递增法

最小代码必须保留本课真正的新结构，并尽量砍掉非核心外层。

```text
最小核心 Python
↓
用户先自己读
↓
如果懂 → 下一课
↓
如果不懂 → 往下看辅助读码信息
↓
必要时 Diagnose → Backfill → Return
↓
回到本课完整代码
```

限制：

- 不能改变真实输入、处理、输出关系。
- 当前核心循环、条件、函数、容器不能被替换成另一种逻辑。
- 可以缩小真实 Poker 数据规模帮助理解，但必须映射回真实项目。
- 可以临时改变量名帮助理解，但必须说明映射。
- 如果某一行再删除就破坏核心逻辑，明确说：**“这一行是核心，不能再砍了。”**

## 8. 每课强制代码识字层：颜色、token、名字、符号

### 8.1 每次都写，不因“以前讲过”自动省略

用户当前仍在建立 Python 代码识字能力，因此**只要本课出现 Python，就必须每课写代码识字辅助**。

即使某个 token 或符号以前讲过，也至少做紧凑提醒；本课新出现、换了上下文、容易混淆的内容则详细讲。

目标是逐渐形成：

```text
看到 PyCharm 颜色
↕
识别 token 属性
↓
知道这个名字是谁提供 / 能不能改
↓
看懂当前位置的符号
↓
读出这一行代码在做什么
```

### 8.2 PyCharm 颜色 ↔ token 属性

必须区分：

```text
代码属性 ≠ 当前语义角色
```

例如 `return` 的代码属性是 Python 关键字，它在当前函数里的语义角色才是“把结果交出去”。

- 用户当前 PyCharm 截图 / 配色已知时，直接说明实际颜色。
- 未知时不猜具体颜色名称，但必须说明 token 类别。
- PyCharm 当前截图 / Color Scheme 是颜色 Source of Truth。

### 8.3 属性小卡里的代码片段必须尽量保留代码高亮

属性说明中出现的 `state`、`if`、`==`、字符串、方法名等 token，应尽量用 Python 语法高亮形式展示，而不是只作为普通正文。

颜色说明必须落到真实代码 token 上；不得为了颜色说明新增第三段完整主逻辑代码。

### 8.4 Python 名字来源每课辅助

帮助用户判断：**这个词是谁规定 / 提供的？能不能改名？**

```text
def / return / for / in / if / else / elif
→ Python 关键字

print / len / range / list / dict
→ Python 内置函数 / 内置类型

append / get / keys / items
→ 标准类型自带方法

__init__ / __len__
→ Python 特殊方法 / 协议名称

create_card / combo / action / deck / state
→ 程序员 / 项目自己起的名字
```

不要把关键字、内置函数、类型方法、特殊方法、标准库、第三方库和项目命名混成一类。

### 8.5 Python 符号 / 标点每课辅助，而且必须按上下文解释

不要默认用户已经知道符号。每课都说明本课关键符号，尤其是第一次出现、换作用或容易混淆的符号。

```text
[]   → list、下标 / key 取值、切片等；按当前位置解释
()   → 函数调用、参数区域、tuple / 分组等；按当前位置解释
{}   → dict / set；按当前位置解释
:    → 代码块开始、切片、dict 键值分隔等
,    → 分隔参数、元素、键值项等
.    → 从对象上访问属性 / 方法
=    → 赋值
==   → 比较是否相等
!=   → 比较是否不相等
< > <= >= → 大小比较
+ - * / // % ** → 当前运算含义
->   → 函数返回类型标注
_    → 名字的一部分或 Python 命名习惯
#    → 注释开始
"" / '' → 字符串边界
```

核心规则：

> **必须说“这里的符号是什么”，不能把符号死背成单一含义。**

## 9. 四个骨架问题 + 数据流

遇到函数或一段小逻辑时，辅助层优先回答：

```text
功能名字是什么？
输入是什么？
里面怎么处理？
输出是什么？
```

再补：谁调用它、数据从哪里来、结果到哪里去、它在 Poker AI 的哪一层。

真实数据优先沿用本课两段代码追一轮：

```text
输入值
→ 参数 / state / 容器
→ 当前处理
→ return / action / 结果
```

真正连接变量的是赋值、参数传递、`return`、容器写入等数据流，不是名字相同。

## 10. 每课强制直观比喻 / 解释层

两段主代码和代码识字层之后，每课都补一个**和当前结构一一对应**的直观比喻或人话模型。

可用：仓库 / 抽屉 / 标签 / 前台 / 流水线 / 门禁 / 路线图 / 牌桌状态盒子等。

要求：

- 比喻必须能映射回真实 Python，不可改变逻辑。
- 说明“比喻中的谁 = 代码里的谁”。
- 比喻只是帮助理解，最终必须回到 Python 术语。
- 不为了好听引入错误概念。

---

## 11. 每课强制代码哲学

每课辅助层最后补一小段**和当前代码直接相关的代码哲学 / 设计思维**，帮助用户逐渐理解“为什么程序员会这样组织代码”。

优先讨论：

```text
数据和行为为什么分开
为什么少重复比复制粘贴好
为什么名字是给人读的，不只是给机器读的
为什么数据驱动通常比堆 if 更容易扩展
为什么函数边界能降低复杂度
为什么明确的数据流比同名巧合更可靠
为什么可读性 / 可验证性比炫技重要
Small → Correct → Scale
```

限制：

- 必须紧贴本课代码，不写空泛鸡汤。
- 默认 2～5 句话即可。
- 代码哲学不能抢第一屏，也不能替代具体 Python 解释。
- 后续进入 Dataset、Model、CFR、Search 时继续沿用，让用户形成工程思维。

---

## 12. 强制疑问诊断：Diagnose → Backfill → Return

用户一旦提出疑问、表示看不懂、问“为什么”或对符号 / 代码结构产生困惑，先判断：

> **这个疑问是不是暴露了以前某个前置基础没有真正学稳？**

固定流程：

```text
当前疑问
↓
Diagnose：找到最小缺失基础
↓
Backfill：用最小 Python 补这一层
↓
真实值 / 短问题确认
↓
Return：回到本课原来的代码
```

优先检查：代码识字 → Python 基础 → 控制结构 → 数据流 → 作用域 / 对象 / 方法 → Poker 项目 → 数学 / AI。

“以前讲过”不等于“已经学会”。只补最小缺口，不整章重讲。

---

## 13. 为什么这样写

重要代码在辅助层补最有价值的一项即可：

```text
为什么这样写？
不这样写会怎样？
删掉这一行会怎样？
换一种写法，核心逻辑哪里相同 / 不同？
```

不要四项机械全部展开。

---

## 14. 抽查与掌握判断

可以偶尔主动抽查 1～2 个已经讲过的问题。优先检查：读代码、识别颜色 / token / 符号、预测结果、解释关键行、真实值数据流、迁移到相似 Python。

用户直接说“下一课 / 继续”时，不为了抽查阻塞课程。

---

## 15. 验证状态

严格区分：

```text
已讲解
已理解
预期可运行
实际运行验证
```

只有用户贴出运行结果或明确确认真实运行成功，才能记录为“已验证”。

## 16. AI / 数学方向

所有正式实现使用 Python：Solver 数据、NumPy / Pandas、Dataset / DataLoader、Tensor、PyTorch、Loss / Optimizer、GPU、模型训练 / 评估 / 推理、Game Tree / Search、CFR / Regret、部署。

默认节奏：Python 代码出现需求 → 补必要数学 / AI → 马上用 Python 表达 → 看真实数据 / 输出 → 回 Poker AI。
