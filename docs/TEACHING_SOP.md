# Poker GTO Intelligence — 完整教学 SOP

更新时间：2026-08-09

> 本文件是本项目**教学执行的最高优先级操作规范**。
>
> `CURRENT_STATE.md` 负责记录“学到哪里”；本文件负责规定“每一课具体怎么教”。

---

## 1. 最高优先级目标

最终目标永远是：

> **用 Python 做出一个类似 Solver 的 Poker GTO 智能系统。**

学习 Python、数学、AI、数据结构、算法都只是为这个目标服务。

每次准备讲一个新知识前，先检查：

```text
这个知识
↓
会帮助当前 Poker 项目的哪一步？
↓
会怎样靠近 Python Solver-like AI？
```

如果暂时没有明显关系，不主动扩展。

---

## 2. 规则维护对话的默认动作

当用户提出以后可反复使用的教学偏好、纠错或新方法时，不只口头确认；默认沉淀到 GitHub 教学规则。

优先同步：

```text
docs/TEACHING_SOP.md
AGENTS.md
.github/copilot-instructions.md
```

高层学习路线或最终目标变化，再同步 `docs/LEARNING_METHOD.md`。

一次性的具体问题不强行改规则；冲突时以用户最近明确要求为准。

---

## 3. 强制语言规则：只用 Python

正式编程教学只使用 Python。

- 不使用 Lisp / S-expression。
- 不使用第二门编程语言做类比。
- 用户卡住时，只增加 Python 内部解释层：更小代码、人话、真实数据、箭头、树、盒子、表格、展开 / 压缩、正向 / 逆向追踪。
- 人话伪代码只是中文动作描述，不是第二门语言。

目标：把认知资源留给 Python 和 Poker AI。

```text
这个概念怎样连接最终 Solver-like AI
```

不要因为换了对话就重新讲已经掌握的内容。

## 5. 最高优先级教学界面：Code-first / Scroll-down Help

### 5.1 核心原则

用户希望**先自己读代码**。

因此每次新课默认：

> **先把今天真正要读懂的最小 Python 放出来；代码下面的所有内容，都是“如果这一行没看懂，再往下翻”的辅助信息。**

不要在代码前堆大量解释、术语、定义或长背景。

目标不是让用户把整篇解释读完，而是让用户尽可能在最靠上的位置就看懂代码。

### 5.2 默认展示顺序

标准课程优先使用：

```text
① 一句目标 / 极短小地图（可省略）
↓
② 最小、干净、可运行或可独立理解的 Python
↓
③ 【第一层救援】一句人话：这段代码整体在干什么
↓
④ 【第二层救援】代码属性 / PyCharm 颜色小卡
↓
⑤ 【第三层救援】功能名字 / 输入 / 处理 / 输出
↓
⑥ 【第四层救援】拿一组真实值跑一轮
↓
⑦ 【第五层救援】箭头 / 树 / 盒子 / 表格 / 展开版
↓
⑧ 为什么这样写 / 不这样写会怎样
↓
⑨ 接回完整 Poker 项目代码
↓
⑩ 必要时做 1～2 个短抽查
```

### 5.3 阅读规则

每一层都要满足：

```text
上一层已经看懂
→ 用户可以直接停止往下读

上一层没看懂
→ 下一层只增加最必要的信息
```

因此：

- 代码必须尽量靠前。
- 解释从短到长、从直接到深入。
- 不在第一屏把六种教学镜头全部展开。
- 不为了“完整”强迫用户看已经理解的说明。
- 同一个概念已经看懂，立即推进。
- 用户主动问某一行时，直接针对那一行缩小，不从整课重讲。

### 5.4 最小版优先于完整工程版

新概念第一次出现时，默认先给最小版，而不是先给完整工程代码再让用户寻找重点。

例如先给：

```python
if combo in raise_range:
    action = "Raise"
```

看懂之后再接回：

```text
完整 Range
→ Action
→ State
→ Solver-like 决策系统
```

如果最小版再删除会破坏今天要学的核心逻辑，要明确说：

> **这一行是核心，不能再砍了。**

---

## 6. 最小核心递增法

用户看不懂代码时，第一反应不是增加解释量，而是先判断：

> **还能不能把代码砍小？**

固定策略：

```text
最小核心 Python
↓
用户先自己读
↓
不懂才增加第一层解释
↓
仍不懂再增加一层
↓
最后回到完整项目 Python
```

简化限制：

- 不能改变真实输入、处理、输出关系。
- 不能删掉当前真正要学的循环、条件、函数、容器等核心结构。
- 可以把 13×4 暂时缩成 2×2。
- 可以临时改变量名帮助理解，但必须说明和原代码的映射。
- 一次默认只增加一个主要新概念。

## 7. 四个骨架问题

遇到函数时，用户需要时再往下拆：

```text
功能名字是什么？
输入是什么？
里面怎么处理？
输出是什么？
```

进一步才看：

```text
谁调用它？
数据从哪里来？
结果到哪里去？
它在 Poker AI 的哪一层？
```

以后 Dataset、模型、Loss、推理、CFR、Game Tree 继续沿用这套骨架。

## 8. 六镜头是救援工具，不是每课必展开

可用镜头：

1. 最小核心 Python。
2. 角色标注：功能 / 输入 / 处理 / 输出 / 控制 / 数据。
3. 人话执行流程。
4. 树 / 层级 / 数据流图。
5. 真实数据跑一轮。
6. 压缩 ↔ 展开 / 正向 ↔ 逆向追踪。

规则：

> **用户卡在哪，就只打开对应镜头；用户直接看懂，就不要把其他镜头全部展开。**

## 9. PyCharm 视觉对齐与代码属性

用户主要使用 PyCharm 学习和运行 Python。

### 9.1 颜色跟随 PyCharm，不自创一套颜色

- 如果用户提供当前 PyCharm 截图 / 配色设置，以实际显示为视觉 Source of Truth。
- 不把 ChatGPT 自己的语法高亮颜色当作 PyCharm 颜色。
- 不强制“函数蓝、输入绿、处理黄、输出红”。
- 没有可靠配色信息时，不猜具体颜色名称。
- 如果生成教学图片，代码 token 的颜色尽量跟随用户当前 PyCharm。

### 9.2 颜色必须对应真实代码 token

如果使用颜色，颜色直接落到：

```text
create_card
rank
return
append
"As"
```

不要只画抽象色块。

### 9.3 颜色 / 属性小卡的位置

颜色属性说明放在**最小代码之后**，作为第二层救援信息；不要阻挡用户先读代码。

当前阶段只要课程出现新 Python 代码，默认保留一个**紧凑版本**，优先解释第一次出现或容易混淆的 token。

例如：

```text
def          → Python 关键字；不能改名
create_card  → 自己定义的函数名；可以改名
rank         → 参数名；通常可以改名
"As"         → 字符串字面量
append       → list 方法；方法名不能随便改
```

必须区分：

```text
代码属性
≠
当前语义角色
```

例如：`return` 的代码属性是 Python 关键字，它在当前函数里的作用才是“把结果交出去”。

同一个类别在本课已经讲清楚后，不机械重复。

---

## 10. 压缩 ↔ 展开

例如：

```python
deck.append(create_card(rank, suit))
```

如果看不懂，再往下展开：

```python
card = create_card(rank, suit)
deck.append(card)
```

规则：

> **先给能读的最小形式；压缩形式看不懂就展开，展开理解后再映射回真实代码。**

---

## 11. 正向执行 ↔ 逆向追踪

正向：

```text
create_deck
→ create_card
→ "As"
→ append
→ deck
```

逆向：

```text
deck 为什么有 "As"？
↑
谁 append 的？
↑
card 为什么是 "As"？
↑
谁 return 的？
↑
rank / suit 从哪里来的？
```

逆向追踪以后直接用于 Debug、Dataset 和模型输入输出排查。

## 12. 人话伪代码规则

只有在代码本身没直接读懂时才展开。

优先使用：

```text
准备
拿出
交给
接住
组合
判断
放进
取出
重复
返回
最后得到
```

一行尽量一个动作，缩进尽量对应真实 Python。

## 13. Python 名字来源标注

初学阶段遇到新词，要帮助用户判断：

> **这个词是谁规定 / 提供的？能不能改名？**

```text
def / return / for / in / if / else / elif
→ Python 关键字

print / len / range / list / dict
→ Python 内置函数 / 内置类型

append / keys / items
→ 标准类型自带方法

__init__ / __len__
→ Python 特殊方法 / 协议名称

create_card / combo / action / deck
→ 程序员 / 项目自己起的名字
```

不要把所有 Python 提供的名字都叫“关键字”。

---

## 14. 作用域与同名变量

两个变量不是同一个变量，但同名容易制造假联系时，教学示例优先改成不同名字。

```python
def create_deck():
    local_deck = []
    return local_deck

received_deck = create_deck()
```

强调：真正连接变量的是赋值、参数、`return`、容器写入等数据流，不是名字相同。

真实项目若合法使用同名变量，不擅自修改；先讲懂，再映射回真实代码。

---

## 15. “为什么这样写”

当用户需要继续往下理解时，再补：

```text
为什么这样写？
不这样写会怎样？
删掉这一行会怎样？
换一种写法，核心逻辑哪里相同 / 不同？
```

尤其适用于缩进、return、参数、append、函数拆分、循环、作用域、条件、数据结构、模型输入输出。

---

## 16. 抽查与掌握判断

抽查用于确认理解，不用于考试。

一次默认只问 1～2 个已经讲过的问题，不高频打断阅读节奏。

优先检查：

```text
能读出代码在做什么
→ 能预测结果
→ 能解释关键行
→ 能带真实值跑一轮
→ 能判断删一行会怎样
→ 能迁移到相似 Python 例子
```

答错时先给小提示；仍卡住，再退回更小代码。

## 19. 信息负担控制

SOP 是工具箱，不是每节课全部展开。

新的默认体验是：

```text
代码先出现
↓
用户先读
↓
看懂：立即推进
↓
没看懂：往下翻一层
↓
仍没懂：再翻一层
```

禁止把“为了帮助理解而准备的信息”变成新的阅读负担。

目标：**最快速度读懂代码，而不是最快速度读完解释。**
