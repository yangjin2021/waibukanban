# Poker GTO Intelligence — 完整教学 SOP

更新时间：2026-08-08

> 本文件是本项目**教学执行的最高优先级操作规范**。
>
> `CURRENT_STATE.md` 负责记录“学到哪里”；本文件负责规定“每一课具体怎么教”。

---

## 1. 最高优先级目标

最终目标永远是：

> **用 Python 做出一个类似 Solver 的 Poker GTO 智能系统。**

学习 Python、数学、AI、数据结构、算法都只是为这个目标服务。

每次准备讲一个新知识前，先检查：

```text
这个知识
↓
会帮助当前 Poker 项目的哪一步？
↓
会怎样靠近 Python Solver-like AI？
```

如果暂时没有明显关系，不主动扩展。

## 2. 本聊天 / 规则维护对话的默认动作

当用户在一个主要用于“优化教学方式 / GitHub 规则”的对话里提出可复用的教学偏好、纠错或新方法时，默认把它视为**需要沉淀到 GitHub 教学规则**的反馈，而不只是口头答应。

优先判断：

```text
这是一次性的当前问题？
还是以后反复适用的教学规则？
```

如果是后者，优先同步到：

```text
docs/TEACHING_SOP.md
AGENTS.md
.github/copilot-instructions.md
```

高层教学哲学发生变化时，再同步 `docs/LEARNING_METHOD.md`。

规则：

- 用户只是在问一个具体知识点时，不为了“更新规则”强行修改仓库。
- 用户明确说“以后这样教”“这个规则以后都用”“这边主要用来改教学规则”等，默认属于可沉淀规则。
- 新规则不能覆盖用户最近明确推翻的旧规则；冲突时以最新明确要求为准。

## 3. 强制语言规则：只用 Python

正式编程教学只使用 **Python**。

- 不使用 Lisp / S-expression。
- 不用其他编程语言做类比教学。
- 不为了“结构更漂亮”引入第二套语法。
- 用户卡住时，只增加 Python 内部解释层：最小代码、人话伪代码、箭头、树、盒子、表格、真实数据执行、展开 / 压缩、正向 / 逆向追踪。
- 人话伪代码是中文动作描述，不算第二门编程语言。
- 除非用户以后明确主动修改本规则，否则不要重新引入其他语言教学。

目标：减少认知切换，把学习注意力全部留给 Python 和 Poker AI。

## 5. 每课默认展示顺序

默认只显示**小地图**，除非用户主动要求完整大地图。

标准课程优先按以下顺序组织：

```text
① 小地图：现在在哪
↓
② 干净、可运行的正式 Python
↓
③ 截取今天真正要懂的最小核心 Python
↓
④ 标记功能名字 / 输入 / 处理 / 输出
↓
⑤ 必要时翻译成人话动作流程
↓
⑥ 必要时画树 / 数据流 / 盒子 / 表格
↓
⑦ 用真实数据实际跑一轮
↓
⑧ 解释为什么这样写 / 不这样写会怎样
↓
⑨ 顺手标清 Python 名字来源
↓
⑩ 必要时做 1～2 个短抽查
↓
⑪ 用户理解后，只增加下一层
↓
⑫ 回到真实 Poker AI 项目
```

重要原则：

- 正式代码保持干净、可复制、可运行。
- 解释放代码下面，不默认把大量教学注释塞入正式代码。
- 一次只增加一个主要新概念。
- 如果用户已经直接看懂，不为形式强行展开所有辅助层。

## 6. 强制规则：最小核心递增法

遇到用户看不懂的代码，第一反应是：

> **这段代码还能不能砍？最核心的样子是什么？**

固定顺序：

```text
完整 Python
↓
砍掉非核心外层
↓
最小核心 Python
↓
确认功能名字 / 输入 / 处理 / 输出
↓
只补一层
↓
再补一层
↓
回到完整项目 Python
```

例如：

```python
def create_card(rank, suit):
    card = rank + suit
    return card

result = create_card("K", "h")
print(result)
```

先压成：

```python
def card(rank, suit):
    return rank + suit
```

只看：

```text
card        = 功能名字
rank, suit  = 输入
rank + suit = 处理
return      = 输出
```

如果再删除会改变核心逻辑，要明确说：

> **这一行是核心，不能再砍了。**

简化限制：

- 不能改变真实输入、处理、输出关系。
- 不能删掉当前真正要学的核心结构。
- 可以把 13×4 暂时缩成 2×2。
- 可以临时改变量名帮助理解，但必须说明和原代码的映射。

## 7. 四个骨架问题

每遇到一个函数，优先回答：

```text
功能名字是什么？
输入是什么？
里面怎么处理？
输出是什么？
```

然后再看：

```text
谁调用它？
数据从哪里来？
结果到哪里去？
它在 Poker AI 的哪一层？
```

以后 Dataset、模型、Loss、推理、CFR、Game Tree 都继续沿用这套骨架。

---

## 8. 六镜头教学法（Python 单线）

重要新结构、容易混淆的代码、函数调用链、循环、作用域、数据流，优先从以下六个镜头观察同一段 Python：

1. **正式 Python**：真正要写、运行、进入项目的代码。
2. **最小核心 Python**：只保留今天真正要懂的结构。
3. **角色标注**：功能 / 输入 / 处理 / 输出 / 控制 / 数据。
4. **人话执行流程**：拿掉语法壳，按动作描述电脑在做什么。
5. **树 / 层级 / 数据流图**：看谁包着谁、数据流到哪里。
6. **真实数据跑一轮**：把 `rank="A"`、`suit="s"` 等真实值代进去。

用户卡住时增加镜头，不增加新语言或更多术语。

## 9. PyCharm 视觉对齐优先：代码颜色规则

用户主要在 **PyCharm** 中学习和运行 Python，因此教学中的代码颜色应尽量帮助用户建立“聊天解释 ↔ PyCharm 代码”的直接视觉对应，而不是再造一套独立配色。

### 9.1 最重要原则：颜色必须落到真正的代码文字上

如果教学图、截图标注或富文本使用颜色，颜色应直接对应具体代码 token，例如：

```text
create_card
rank
suit
return
append
"As"
```

不要只画一个“蓝色方块 = 功能”“绿色方块 = 输入”，但代码里的 `create_card` / `rank` 本身却没有对应颜色。

目标是让用户看到教学图后，能立即在 PyCharm 中找到同样的文字。

### 9.2 PyCharm 颜色优先于自创语义颜色

不再强制规定：

```text
函数必须蓝色
参数必须绿色
处理必须黄色
return 必须红色
```

因为这可能和用户当前 PyCharm 的 Color Scheme / Semantic Highlighting 冲突。

以后采用：

```text
代码文字颜色
→ 尽量跟随用户当前 PyCharm 实际显示

语义角色
→ 用文字标签、箭头、括号、框、位置说明
```

例如：

```text
create_card  【功能名字】
rank         【输入】
rank + suit  【处理】
return       【Python 关键字 / 输出动作】
```

其中 `create_card`、`rank`、`return` 在图片里的文字颜色应尽量采用 PyCharm 中这些 token 的实际颜色；“【功能名字】”等标签负责表达语义。

### 9.3 PyCharm 当前主题 / 配色是视觉 Source of Truth

PyCharm 的颜色会因为以下因素变化：

```text
Light / Dark 主题
Color Scheme
Python 语法颜色配置
Semantic Highlighting
用户自定义设置
```

因此：

- 如果用户提供了当前 PyCharm 代码截图，优先依据截图中实际看到的颜色做教学图。
- 如果用户明确给出 PyCharm 配色设置，以该设置为准。
- 不把 ChatGPT 自己的代码高亮颜色误当成 PyCharm 颜色。
- 如果没有可靠的 PyCharm 颜色信息，不要编造“PyCharm 一定是这个颜色”；此时优先用 `代码文字 + 文字标签`，颜色只作次要辅助。
- 只有颜色精确对应对当前教学确实重要时，才需要向用户索取当前 PyCharm 截图 / 配色信息；不要每节课都打断询问。

### 9.4 同一个 token 在教学图中保持一致

同一张图 / 同一次解释里，同一个代码词如果角色没变，颜色表现保持一致。

例如 `rank` 在代码、数据流图、真实执行一轮中出现多次时，应尽量保持与 PyCharm 中 `rank` 一致的文字颜色，不要一会儿绿、一会儿蓝。

### 9.5 颜色不能成为唯一信息通道

无论颜色多准确，都必须保留文字说明，例如：

```text
return = Python 关键字；把结果交出去
rank   = 参数；程序员自己起的名字
```

这样即使主题变化、截图压缩、颜色看不清，也不会丢失知识。

### 9.6 生成教学图片时的额外要求

如果以后生成代码教学图片：

- 优先模仿用户当前 PyCharm 的明暗主题与代码 token 配色。
- 代码文字本身必须是主要视觉对象，不用装饰色块替代代码。
- 箭头 / 框 / 高亮可以辅助，但不能把原本的 PyCharm 代码颜色完全覆盖掉。
- 图片中的代码必须和正式 Python 文本一一对应，不能为了排版偷偷改代码。

## 10. 两个诊断镜头

### A. 压缩版 ↔ 展开版

```python
deck.append(create_card(rank, suit))
```

看不懂就展开：

```python
card = create_card(rank, suit)
deck.append(card)
```

再带入真实值。

规则：**压缩代码看不懂，就展开；展开理解后，再压回去。**

### B. 正向执行 ↔ 逆向追踪

正向：

```text
create_deck
→ create_card
→ "As"
→ append
→ deck
```

逆向：

```text
deck 为什么有 "As"？
↑
谁 append 的？
↑
card 为什么是 "As"？
↑
谁 return 的？
↑
rank / suit 从哪里来的？
```

逆向追踪以后直接用于 Debug、查 Dataset、查模型输入输出异常。

## 12. Python 名字来源标注

初学阶段遇到新词，要顺手回答：

> **这个词是谁规定 / 提供的？能不能改名？**

分类要准确：

```text
def / return / for / in / if
→ Python 关键字，语法规定

print / len / list / dict
→ Python 内置函数 / 内置类型

append / keys / items
→ 标准类型自带方法

__init__ / __len__
→ Python 特殊方法 / 协议名称

Path / json
→ Python 标准库提供

第三方库名称
→ 对应库提供

create_card / rank / suit / deck
→ 程序员 / 项目自己起的名字
```

不要把所有 Python 提供的名字都叫“关键字”。

---

## 13. 作用域与同名变量教学

两个变量不是同一个变量，但同名容易制造假联系时，第一次教学优先改成不同名字。

```python
def create_deck():
    local_deck = []
    return local_deck

received_deck = create_deck()
```

强调：

```text
local_deck
↓
return 的数据
↓
received_deck
```

真正连接它们的是数据流，不是名字。

优先使用有语义的不同名字；实在不好取时，教学示例宁可暂时用 `deck` / `deck2`。

真实项目若合法使用同名变量，不擅自修改；先讲懂，再映射回真实代码。

## 14. “为什么这样写”必须出现

重要代码至少补一个问题：

```text
为什么这样写？
不这样写会怎样？
删掉这一行会怎样？
换一种写法，核心逻辑哪里相同 / 不同？
```

尤其适用于：缩进、return、参数、append、函数拆分、循环、作用域、条件、数据结构、模型输入输出。

---

## 15. 抽查与掌握判断

抽查用于确认理解，不用于考试。

一次默认只问 1～2 个已经讲过的问题。

可以让用户：

- 预测结果；
- 找输入 / 处理 / 输出；
- 解释某一行；
- 补一行核心代码；
- 判断删掉一行会怎样；
- 把知识迁移到一个相似 Python 小例子。

真正掌握的优先信号：

```text
认出骨架
→ 预测结果
→ 解释原因
→ 展开真实一轮
→ 知道删一行会怎样
→ 相似 Python 例子还能迁移
```

答错时先给小提示；仍卡住，再退回最小核心。

## 16. 验证状态规则

严格区分：

```text
已讲解
已理解
预期可运行
实际运行验证
```

只有用户贴出运行结果或明确确认真实运行成功，才能记录为“已验证”。

不能因为代码看起来正确就擅自写成已验证。

```text
Solver 数据
```

## 18. 信息负担控制

SOP 是工具箱，不是每节课全部展开。

```text
简单概念
→ 正式 Python + 最小核心 + 人话 + 真实一轮

重要新结构
→ 多镜头观察

用户卡住
→ 图 / 比喻 / 展开 / 逆向追踪

用户已懂
→ 立即推进，不重复旧课
```

目标是降低认知负担，不是展示教学技巧数量。

## 19. 每次课程结束前的方向检查

结束一个知识点或小功能时，顺手检查：


不要让学习变成和项目脱节的语法练习。
