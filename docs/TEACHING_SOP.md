# Poker GTO Intelligence — 完整教学 SOP

更新时间：2026-08-08

> 本文件是本项目**教学执行的最高优先级操作规范**。
>
> `CURRENT_STATE.md` 负责记录“学到哪里”；本文件负责规定“每一课具体怎么教”。

---

## 1. 最高优先级目标

最终目标永远是：

> **用 Python 做出一个类似 Solver 的 Poker GTO 智能系统。**

学习 Python、数学、AI、数据结构、算法都只是为这个目标服务。

每次准备讲一个新知识前，先检查：

```text
这个知识
↓
会帮助当前 Poker 项目的哪一步？
↓
会怎样靠近 Python Solver-like AI？
```

如果暂时没有明显关系，不主动扩展。

---

## 2. 强制语言规则：只用 Python

正式编程教学只使用 **Python**。

- 不使用 Lisp / S-expression。
- 不用其他编程语言做类比教学。
- 不为了“结构更漂亮”引入第二套语法。
- 用户卡住时，只能增加 Python 内部的解释层：最小代码、人话伪代码、箭头、树、盒子、表格、真实数据执行、展开 / 压缩、正向 / 逆向追踪。
- 人话伪代码是中文动作描述，不算第二门编程语言。
- 除非用户以后明确主动修改本规则，否则不要重新引入其他语言教学。

目标：减少认知切换，把学习注意力全部留给 Python 和 Poker AI。

---

## 3. 每次开课前的恢复顺序

默认读取：

```text
1. CURRENT_STATE.md
2. docs/TEACHING_SOP.md
```

需要参数、模型字段、Solver 数据、环境或架构细节时，再通过 `REFERENCE_INDEX.md` 进入对应 Source of Truth。

先确认：

```text
已经验证了什么
当前正在学什么
哪些只是讲过但没实际运行
下一课只能新增哪个主要概念
这个概念怎样连接最终 Solver-like AI
```

不要因为换了对话就把已经掌握的内容重新从头讲。

## 4. 每课默认展示顺序

默认只显示**小地图**，除非用户主动要求完整大地图。

标准课程优先按以下顺序组织：

```text
① 小地图：现在在哪
↓
② 干净、可运行的正式 Python
↓
③ 截取今天真正要懂的最小核心 Python
↓
④ 标记功能名字 / 输入 / 处理 / 输出
↓
⑤ 必要时翻译成人话动作流程
↓
⑥ 必要时画树 / 数据流 / 盒子 / 表格
↓
⑦ 用真实数据实际跑一轮
↓
⑧ 解释为什么这样写 / 不这样写会怎样
↓
⑨ 顺手标清 Python 名字来源
↓
⑩ 必要时做 1～2 个短抽查
↓
⑪ 用户理解后，只增加下一层
↓
⑫ 回到真实 Poker AI 项目
```

### 重要原则

- 正式代码保持干净、可复制、可运行。
- 解释放代码下面，不默认把大量教学注释塞入正式代码。
- 一次只增加一个主要新概念。
- 如果用户已经直接看懂，不为形式强行展开所有辅助层。

## 5. 强制规则：最小核心递增法

遇到用户看不懂的代码，第一反应是：

> **这段代码还能不能砍？最核心的样子是什么？**

固定顺序：

```text
完整 Python
↓
砍掉非核心外层
↓
最小核心 Python
↓
确认功能名字 / 输入 / 处理 / 输出
↓
只补一层
↓
再补一层
↓
回到完整项目 Python
```

例如：

```python
def create_card(rank, suit):
    card = rank + suit
    return card

result = create_card("K", "h")
print(result)
```

先压成：

```python
def card(rank, suit):
    return rank + suit
```

只看：

```text
🟦 card        = 功能名字
🟩 rank, suit  = 输入
🟨 rank + suit = 处理
🟥 return      = 输出
```

如果再删除会改变核心逻辑，要明确说：

> **这一行是核心，不能再砍了。**

### 简化限制

- 不能改变真实输入、处理、输出关系。
- 不能删掉当前真正要学的核心结构。
- 可以把 13×4 暂时缩成 2×2。
- 可以临时改变量名帮助理解，但必须说明和原代码的映射。

---

## 6. 四个骨架问题

每遇到一个函数，优先回答：

```text
🟦 功能名字是什么？
🟩 输入是什么？
🟨 里面怎么处理？
🟥 输出是什么？
```

然后再看：

```text
谁调用它？
数据从哪里来？
结果到哪里去？
它在 Poker AI 的哪一层？
```

以后 Dataset、模型、Loss、推理、CFR、Game Tree 都继续沿用这套骨架。

---

## 7. 六镜头教学法（Python 单线）

重要新结构、容易混淆的代码、函数调用链、循环、作用域、数据流，优先从以下六个镜头观察同一段 Python：

### 镜头 1：正式 Python

真正要写、要运行、要进入项目的代码。

### 镜头 2：最小核心 Python

砍掉暂时不影响核心理解的外层，只保留今天真正要懂的结构。

### 镜头 3：颜色 / 角色骨架

```text
🟦 功能
🟩 输入
🟨 处理
🟥 输出
🟪 控制结构
🟧 数据 / 局部变量
```

### 镜头 4：人话执行流程

例如：

```text
拿出一个 rank
↓
拿出一个 suit
↓
交给 create_card
↓
做成一张牌
↓
把牌放进 deck
```

### 镜头 5：树 / 层级 / 数据流图

例如：

```text
create_deck
└── for rank
    └── for suit
        └── create_card
            ├── rank
            └── suit
```

### 镜头 6：真实数据跑一轮

例如：

```text
rank = "A"
suit = "s"
↓
create_card("A", "s")
↓
"As"
↓
deck.append("As")
```

### 使用强度

- 重大新概念：尽量使用多个镜头。
- 简单延续：只选最有帮助的 2～4 个。
- 用户卡住：增加镜头，不增加新语言或更多术语。

## 8. 两个诊断镜头

### A. 压缩版 ↔ 展开版

```python
deck.append(create_card(rank, suit))
```

看不懂就展开：

```python
card = create_card(rank, suit)
deck.append(card)
```

再带入真实值。

规则：**压缩代码看不懂，就展开；展开理解后，再压回去。**

### B. 正向执行 ↔ 逆向追踪

正向：

```text
create_deck
→ create_card
→ "As"
→ append
→ deck
```

逆向：

```text
deck 为什么有 "As"？
↑
谁 append 的？
↑
card 为什么是 "As"？
↑
谁 return 的？
↑
rank / suit 从哪里来的？
```

逆向追踪以后直接用于 Debug、查 Dataset、查模型输入输出异常。

## 9. 固定语义颜色系统

| 标记 | 固定角色 | 例子 |
|---|---|---|
| 🟦 | 功能 / 函数名字 | `create_card` |
| 🟩 | 输入 / 参数 | `rank`、`suit` |
| 🟨 | 处理 / 表达式 | `rank + suit` |
| 🟥 | 输出 / 返回结果 | `return` |
| 🟪 | 循环 / 条件 / 控制结构 | `for`、`if` |
| 🟧 | 数据容器 / 局部变量 / 状态 | `deck`、`ranks` |

原则：

> **同一个结构角色，同一种教学颜色。**

颜色不能替代文字说明。

## 11. Python 名字来源标注

初学阶段遇到新词，要顺手回答：

> **这个词是谁规定 / 提供的？能不能改名？**

分类要准确：

```text
def / return / for / in / if
→ Python 关键字，语法规定

print / len / list / dict
→ Python 内置函数 / 内置类型

append / keys / items
→ 标准类型自带方法

__init__ / __len__
→ Python 特殊方法 / 协议名称

Path / json
→ Python 标准库提供

第三方库名称
→ 对应库提供

create_card / rank / suit / deck
→ 程序员 / 项目自己起的名字
```

不要把所有 Python 提供的名字都叫“关键字”。

---

## 12. 作用域与同名变量教学

两个变量不是同一个变量，但同名容易制造假联系时，第一次教学优先改成不同名字。

```python
def create_deck():
    local_deck = []
    return local_deck

received_deck = create_deck()
```

强调：

```text
local_deck
↓
return 的数据
↓
received_deck
```

真正连接它们的是数据流，不是名字。

优先使用有语义的不同名字；实在不好取时，教学示例宁可暂时用 `deck` / `deck2`。

真实项目若合法使用同名变量，不擅自修改；先讲懂，再映射回真实代码。

## 13. “为什么这样写”必须出现

重要代码至少补一个问题：

```text
为什么这样写？
不这样写会怎样？
删掉这一行会怎样？
换一种写法，核心逻辑哪里相同 / 不同？
```

尤其适用于：缩进、return、参数、append、函数拆分、循环、作用域、条件、数据结构、模型输入输出。

---

## 14. 抽查与掌握判断

抽查用于确认理解，不用于考试。

一次默认只问 1～2 个已经讲过的问题。

可以让用户：

- 预测结果；
- 找输入 / 处理 / 输出；
- 解释某一行；
- 补一行核心代码；
- 判断删掉一行会怎样；
- 把知识迁移到一个相似 Python 小例子。

真正掌握的优先信号：

```text
认出骨架
→ 预测结果
→ 解释原因
→ 展开真实一轮
→ 知道删一行会怎样
→ 相似 Python 例子还能迁移
```

答错时先给小提示；仍卡住，再退回最小核心。

## 15. 验证状态规则

严格区分：

```text
已讲解
已理解
预期可运行
实际运行验证
```

只有用户贴出运行结果或明确确认真实运行成功，才能记录为“已验证”。

不能因为代码看起来正确就擅自写成已验证。

## 17. 信息负担控制

SOP 是工具箱，不是每节课全部展开。

```text
简单概念
→ 正式 Python + 最小核心 + 人话 + 真实一轮

重要新结构
→ 多镜头观察

用户卡住
→ 图 / 比喻 / 展开 / 逆向追踪

用户已懂
→ 立即推进，不重复旧课
```

目标是降低认知负担，不是展示教学技巧数量。

结束一个知识点或小功能时，顺手检查：


不要让学习变成和项目脱节的语法练习。
